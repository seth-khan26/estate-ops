# Database Schema

## Design Decisions

### Every domain table carries `organizationId`

All tables except `users`, `accounts`, `sessions`, and `verification_tokens` (auth tables that belong to NextAuth) carry an `organizationId` column that references `organizations.id`. This is the fundamental tenant isolation mechanism. A row without an `organizationId` cannot be scoped to a tenant and therefore cannot appear in any service query.

### `User` vs `Tenant` — two distinct concepts

```
User    — authenticated identity. Can log in. Has sessions.
Tenant  — property-management domain entity. A person renting a unit.
```

These are not the same thing. A tenant renting an apartment may never need a login — their lease and payments are managed entirely by the property manager. The `Tenant` table stores just enough contact information (name, email, phone) to manage the property relationship without requiring an application account.

When a tenant does need a login (e.g. to submit maintenance requests online), a `Membership` row is created linking their `User` to the organization with `role: "TENANT"` and `tenantId` pointing to their `Tenant` record. This is optional at the model level — `Membership.tenantId` is nullable.

### `PropertyOwner` join table

A property can have multiple owners with different ownership percentages. Rather than putting a single `ownerId` on `Property`, there is a `PropertyOwner` join:

```
Property ──── PropertyOwner ──── Owner
                ownershipPercentage
```

This correctly models scenarios like two investors splitting a building 60/40. The `ownershipPercentage` column is informational — the system does not use it to split payment distributions in the MVP.

### `RentCharge` + `Payment` split (not a single payment table)

The rental billing model uses two tables:

- `RentCharge` — what is owed for a period. Generated by the monthly job.
- `Payment` — what was received. Many payments can apply to one charge (partial payments).

An alternative would be a single `transaction` table with positive (charge) and negative (payment) entries — a double-entry ledger style. That approach is more extensible for a full accounting system but significantly more complex to query for common operations ("what does this tenant owe?"). The two-table approach is simpler and sufficient for rent tracking.

### `UNIQUE(leaseId, billingPeriod)` on `RentCharge`

This constraint is the idempotency guarantee for monthly charge generation. The job can be run any number of times — the unique violation for an already-generated period is caught and counted as `skipped`. Without this constraint, every job run would add a duplicate charge.

### Cascade deletes

All domain tables cascade delete from `Organization`. Deleting an organization removes all of its data. This is appropriate for the data model — there is no cross-org data sharing, so orphaned rows from a deleted org are pure waste.

Within an organization:
- `Unit` cascades from `Property` (deleting a property removes its units)
- `PropertyOwner` cascades from both `Property` and `Owner`

Leases, tenants, and rent charges do NOT cascade from units/properties — they are historical records that should be preserved even if the property configuration changes.

### Decimal for money

All monetary fields (`monthlyRent`, `securityDeposit`, `amount`, `ownershipPercentage`) use Prisma's `Decimal` type, which maps to PostgreSQL `NUMERIC`. This avoids floating-point rounding errors in storage. However, the current service code converts `Decimal` to JavaScript `Number` for arithmetic — which reintroduces floating-point risk. A production-ready implementation would use a decimal arithmetic library (e.g. `decimal.js`) throughout.

## Key Indexes

```sql
-- Fast audit log queries by org and time
CREATE INDEX audit_logs_org_created ON audit_logs(organization_id, created_at);

-- Fast history lookup for a specific resource
CREATE INDEX audit_logs_resource ON audit_logs(organization_id, resource_type, resource_id);

-- Fast document lookup by resource
CREATE INDEX documents_resource ON documents(resource_type, resource_id);

-- Unique constraint that enforces one billing charge per lease per period
UNIQUE INDEX rent_charges_lease_period ON rent_charges(lease_id, billing_period);

-- Unit number uniqueness within a property
UNIQUE INDEX units_property_number ON units(property_id, unit_number);
```

## Recommended Production Additions

These constraints are not in the current schema but should be added before production:

```sql
-- Enforce one active lease per unit at the DB level (not just app level)
CREATE UNIQUE INDEX one_active_lease_per_unit
  ON leases(unit_id)
  WHERE status IN ('ACTIVE', 'EXPIRING');

-- Prevent overpayment at the DB level (CHECK constraint)
-- Harder to express as a cross-row constraint; better handled in application with proper locking

-- Row-Level Security policies (one per table)
ALTER TABLE properties ENABLE ROW LEVEL SECURITY;
CREATE POLICY org_isolation ON properties
  USING (organization_id = current_setting('app.current_org_id')::uuid);
-- (repeat for all tenant-scoped tables)
```

## Entity Relationship Summary

```
Organization
├── Membership (User × Organization × Role)
├── Property
│   ├── Unit
│   │   └── Lease (→ Tenant)
│   │       └── RentCharge
│   │           └── Payment
│   ├── PropertyOwner (→ Owner)
│   └── MaintenanceRequest (→ Unit?)
├── Owner
├── Tenant
├── Document (polymorphic: resourceType + resourceId)
├── AuditLog
└── Notification
```

## Core Schema

Models: Organization, Property, Unit, Tenant, Lease, MaintenanceRequest, Payment.
